## Run in an isolated sandbox

Use Node.js 22 and a disposable Intuit developer sandbox with an active Bank
account and Expense account. Supply a current accounting-scope sandbox OAuth
access token and its matching sandbox realm ID through a secure environment:

- `QBO_SANDBOX_REALM_ID`
- `QBO_SANDBOX_ACCESS_TOKEN`

Do not paste tokens into chat, commit them, or put them in shell command
arguments. This probe does not refresh tokens or alter SILO's QBO connection.
Do not flip the production project's `QBO_ENVIRONMENT` or replace its client
keys to run this check.

```sh
# Prints usage without making requests.
node scripts/qbo-sandbox-validation.mjs

# Opts in to creating and deleting one synthetic $0.01 sandbox journal.
node scripts/qbo-sandbox-validation.mjs --run

# Exercises the runner with fake HTTP responses; no credentials or network.
node scripts/tests/qbo-sandbox-validation.test.mjs
```

The live runner uses only `sandbox-quickbooks.api.intuit.com`, refuses
redirects, and imports the same DocNumber, query, payload, and line-comparison
helpers as `quickbooks-post-journal`. It selects existing sandbox accounts,
checks that its unique reference is unused, submits at most one journal,
checks exact lookup and readback, then deletes only the journal verified as
belonging to this run and checks that lookup no longer returns it. It does
not create accounts or touch Supabase.

An ambiguous create response triggers lookup with the same reference, never
another create. Failed lookup, identity mismatch, ambiguous results, or
unverified cleanup must remain a non-passing result. A process interruption
can also leave the synthetic journal behind: retain the run reference from
the output and inspect that exact entry in the sandbox before rerunning.
SILO's **Mark unposted** operation changes local posting state; it does not
delete a journal from QBO and is not cleanup for this probe.
