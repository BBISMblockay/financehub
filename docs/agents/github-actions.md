## GitHub Actions / data sync

| Workflow | Schedule | What it does |
|----------|----------|-------------|
| `shopify-sync.yml` | **08:30 UTC** (full) + **14:30 UTC** (sales catch-up) | Shopify API sync — sales + inventory + catalog + payouts for all connected stores, then refreshes comp summary, sales velocity MV, and inventory current MV. Moved from 11:00 UTC in 2026-08 so the "as of yesterday" date lands before morning check-ins. **Never schedule before 08:00 UTC** — in PST that is before Pacific midnight and the comp summary would anchor a partial day. The 14:30 UTC entry is a catch-up added 2026-08-27 after GitHub silently DROPPED that day's 08:30 run (scheduled triggers are best-effort, and a dropped run leaves no trace in the Actions list — it just never appears). It skips catalog/sessions/landing-pages/discount-codes via `github.event.schedule` and does sales + inventory only; there is deliberately NO `concurrency` group -- one was tried the same day and removed within the hour, because `cancel-in-progress: false` QUEUES a newly-arrived run and a queued run is cancelled the moment another enters the group, so the group can silently kill a scheduled nightly (the exact failure the catch-up exists to prevent) and it did kill a manual run mid-sales. The crons are 6h apart against a ~75min run, so they cannot collide on their own, and every write in the sync is an idempotent upsert |
| `nightly-silo-sync.yml` | **Retired** (manual only) | Legacy Google Sheets / Better Reports import — retired 2026-07-08 after verifying Shopify covers every sales + inventory location. BR history remains in `sales_by_day` for pre-API reporting |
| `sales-freshness-check.yml` | 11:00 / 17:00 / 23:00 UTC | Independent alarm for "a nightly sync did not run". Checks BOTH feeds — `sales_by_day` (via `shopify_connections`) and `marketing_kpis_daily` (via `ad_platform_connections`) — because on 2026-08-27 GitHub dropped `shopify-sync` AND `ad-platforms-sync` on the same morning; checking only sales would have left Meta quietly ~4.5h short on its most recent day. Queries the newest `day_date` per company per feed, and FAILS the run if it is more than `MAX_LAG_DAYS` (default 1) behind the last complete **Pacific** day. **It SELF-HEALS, it does not just alert**: on finding a feed stale it runs that feed's sync INLINE in its own job, then re-checks and only fails if still behind — an alarm alone just moves the firefighting earlier, and the point is that nobody runs a fix on the morning of a meeting. Inline rather than dispatching the other workflow because GitHub blocks workflows triggered by the built-in `GITHUB_TOKEN` from starting new workflow runs (recursion guard); dispatching would need a PAT, a new long-lived credential, while running the same script here needs only the Supabase secrets it already has. When it does fail, reporting is the exit code — a failed Actions run emails the repo owner, so there is no extra secret or webhook to configure or let rot. **It is deliberately a separate workflow, not a step in `shopify-sync.yml`**: a check inside the sync cannot detect a dropped sync, because a dropped sync never reaches the check. That is exactly what happened 2026-08-27. Lag 1 is HEALTHY (sales are only ever complete through yesterday); 2 means a nightly was missed |
| `ar-sync.yml` | Manual / scheduled | AR (accounts receivable) sync |
| `deployment-drift-check.yml` | **12:00 UTC** daily + push to `main` touching `supabase/**` | **Is production in the state the repo claims?** Two read-only jobs, added 2026-09-10 after the push-triggered suites proved good at "does the code do what the code says" and blind to "is prod running it". `schema` runs `verify_v2_schema.sql` against production through the Management API (same `SUPABASE_ACCESS_TOKEN` the deploy workflow holds), one statement at a time via `scripts/lib/sql-statements.mjs` (a naive split on `;` breaks on the first status message containing one), refuses to send anything that is not SELECT/WITH, and fails on any MISSING / CRITICAL / STALE cell — the day it was written, check 6 had been MISSING for a day (12 tables without their company stamp trigger) and nobody knew. `functions` runs `supabase functions download --use-api` over the checkout and lets `git status` say which deployed function differs from `main`, which is deployed with no source here (the four known ones only warn; a new one fails), and which is on `main` but not deployed. **The push trigger means the run right after a migration or function merge is SUPPOSED to be red until someone applies/deploys it** — that red is the reminder, not a flake. **First run (2026-09-10) settled both open questions and found real drift.** `read_only: true` IS accepted, and it runs the statement as a restricted role that sees a different database (information_schema hides constraints on tables it has no privilege on; a function granted only to `authenticated` is permission denied), so two checks came back MISSING/ERROR over a correct schema — the flag is not sent; the SELECT-only guard is the safety. `functions download` DOES re-emit source verbatim, but every function deployed before the sources were checked in (2026-09-02) is stored without a trailing newline, so those are classified separately and do not fail. Real findings the same run: two Ask SILO catalog caveats dropped by later migrations that replaced descriptions instead of appending (restored, `20260910150000`), a verify check testing a comment string a later migration did not carry (fixed), production's `notify_sample_events()` trigger being a hand-edited version no migration contains (open, `docs/ops/bugs.md`), and six functions whose deployed content differs from `main` (open, same place). **All six are now reconciled.** `page-inspect` was the last one deployed from `main` through the workflow (v3, 2026-09-10) — the CLI reads the file, so the retyped comment rules an API-client deploy had introduced could not recur. **A difference somebody deliberately does not reconcile goes in `DEFERRED_DRIFT`** in `scripts/check-function-drift.mjs`, which downgrades it to a warning so the daily run is not red forever (a check that is always red is one nobody reads). Each entry is PINNED to BOTH SIDES of the difference it forgives and both must still match: the `ezbr_sha256` of the deployed bundle (moves when PRODUCTION changes) and the function directory's **git tree** at HEAD (moves when the REPO changes). A bare slug list would swallow the NEXT, different drift in the same function; **pinning production alone is not enough either**, and that was the first version — a change merged to the function and never deployed leaves the deployed hash untouched, so the deferral went on forgiving a difference that had grown (caught in review, 2026-09-10). The repo side is a TREE rather than per-file blobs because `git status` — the check's only other input — cannot see a file committed to the repo that the deployment lacks: the download leaves it alone, so it matches HEAD and reports nothing. A tree covers names and modes as well as content, so one hash catches an edit, an addition, a removal or a rename. Drift has exactly two sources and each moves one of the two pins, so nothing per-file is left to check. A slug with no hash reported, a directory gone from HEAD, and an entry with no tree pin all fail closed. There are no entries (the `card-categorize` deferral was removed 2026-10-07). **A file one function imports from another is downloaded once per bundle that contains it, and the last bundle written wins**: `card-coding-prepare-scheduled` imports `../card-categorize/prepare.ts`, so when it is deployed with an older copy, the check reports `card-categorize/prepare.ts` as differing even though `card-categorize` itself is current. The fix is to redeploy the IMPORTER |
| `report-tieouts-nightly.yml` | **13:17 UTC** daily + manual | **Do the SILO reports still reconcile?** Runs `run_report_tieouts()` for EVERY company, impersonated as one of its own active admins (`set local role authenticated` + JWT claims) inside a transaction that is ROLLED BACK, through the Management API with the drift check's `SUPABASE_ACCESS_TOKEN`. Red on MISMATCH, STALE or ERROR; NO DATA does not fail. **STALE** is the reclassification that matters: most checks pin `md5(queries_run \|\| parameters)` and blank themselves when the report changes, which the SQL runner calls NO DATA -- the nightly compares each pin to the live report instead (`scripts/lib/report-tieouts-nightly.mjs`). A company with no active member whose active company it is is reported as not checked. **When you edit a SILO report, regenerate its tie-outs in the same migration** or this run goes red the next morning |
| `card-coding-prepare.yml` | **10:41 UTC** nightly + manual | The coding-preparation catch-up (CSV imports, dropped or interrupted runs, failures due a retry). `plaid-sync.yml` also runs a `prepare-coding` job after every sync, as a separate job so a preparation failure never marks ingestion red. Both call `scripts/card-coding-prepare.mjs` → `card-coding-prepare-scheduled`; both are skipped unless the repo variable `CODING_PREP_ENABLED` is `true`. No bank calls |
| `seo-serp-sync.yml` | **Mondays 09:15 UTC** + **15:15 UTC** (catch-up) | DataForSEO SERP fetch of each active `seo_serp_schedules` company's keyword set into `seo_serp_runs` / `_run_keywords` / `_observations` via the standard queue, resumable from the `seo_serp_provider_tasks` ledger (the catch-up collects what the deadline left pending and posts nothing). Secrets `DATAFORSEO_LOGIN` / `DATAFORSEO_PASSWORD`. `seo-serp-probe.yml` is the read-only measurement |
| `redo-marketing-sync.yml` | **10:45 UTC** + **16:45 UTC** (catch-up) | Redo campaign + automation reporting into `redo_marketing_*` for every active `redo_connections` row, re-pulling a trailing **60** days (not Redo's documented 5-day window, which the live data exceeds by weeks). Dispatch with `start_date` to backfill (chunked to Redo's 400-day limit, newest first). A token lacking the marketing scopes records `sync_jobs.status = 'skipped'`, not a failure. `redo-marketing-probe.yml` is the read-only check |
| `ad-platforms-sync.yml` | **10:30 UTC** + **16:30 UTC** (catch-up) | Direct platform APIs → `marketing_kpis_daily` (Google Ads, Meta Ads, TikTok Ads, GA4 daily campaign KPIs). Per-connection tokens live on `ad_platform_connections` rows (set via `/v2/integrations.html`); Google connections additionally need the `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_ADS_DEVELOPER_TOKEN` repo secrets and are skipped until those exist. Replaced the retired Supermetrics path (never went live). **Since 2026-09-10 also runs Search Console** connections through `scripts/lib/search-console-sync-core.mjs` into the `search_console_*_daily` tables (own tables, own job_type `search_console_daily`, never `marketing_kpis_daily`); the 2-hourly refresh sets `ADS_SKIP_SEARCH_CONSOLE` because final data moves daily. The Integrations row's Sync toggle is live for it like every other platform and it defaults OFF. **A NEW Meta connection imports a year on its first full run** (2026-10-06, `scripts/lib/meta-history-backfill.mjs`): Integrations stamps `meta.history_backfill_pending` on insert, the next run that does not skip organic pulls 365 days of campaign totals, ad-level rows and Page posts for that one connection, then clears the flag (`history_backfilled_at`); a failure retries up to 3 times, then records `history_backfill_gave_up_at`. The 2-hourly refresh never consumes the flag, and a connection without it is never widened |

**One sync, one source of truth.** Sales and inventory come from the Shopify API via the nightly GitHub Action. There is no dual-write conflict.

Manual-only workflows (`workflow_dispatch`, no cron): `search-console-probe.yml` (read-only measurement of
the Search Console account — lag, retention, row cap, attribution share; re-run it before changing the
`search_console_*_daily` shape), `search-console-backfill.yml` (history into those tables, newest-first in
chunks so a failure keeps what landed; default 500 days ≈ everything Google retains),
`meta-creative-images.yml` (archives every stored creative's 1080px image into the private
`ad-creative-images` bucket for Ad Studio -- the nightly archives only the ads it synced; resumable,
and a run that archives nothing while failing everything exits non-zero),
`meta-creative-probe.yml` (read-only; `mode=images` measures which image fields Meta serves, at what
size and until when), `meta-creative-backfill.yml` (destinations + page-post copy for ads the nightly never asks
about -- it requests creatives only for ad ids inside its trailing window, which is why 126 of 4,079
stored creatives had ever been requested; ONLY ADDS, never blanks a resolved link or recovered copy),
`redo-backfill.yml` (Redo returns REST backfill),
`shopify-orders-backfill.yml` (historical `shopify_orders`/`shopify_order_lines` backfill — order facts
only, no `sales_by_day` involvement, idempotent per range; the nightly sync only covers orders touched in
its ~2-day window going forward), `backfill-company-entity-large-tables.yml`, `mailroom-backfill.yml`,
`legacy-payment-requests-import.yml`, `one-time-sales-backfill.yml`, `diagnose-shopify-gross.yml`,
`diagnose-shopify-returns.yml`.

Secrets required: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (set in GitHub repo settings).
Additionally: `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_ADS_DEVELOPER_TOKEN` for Google ad-platform syncs.
