## Database — Supabase

### Multi-tenant architecture

SILO supports multiple companies in one Supabase project. Isolation is enforced at the DB level.

**Key tables:**
- `entities` — company registry (`entity_type = 'company'`, `entity_key`, `title`)
- `entity_memberships` — links users to companies (`entity_id`, `user_id`, `role`)

**Key column:** `company_entity_id uuid` on all operational tables, fully backfilled — including `inventory_on_hand` and `sales_by_day`, which older notes list as deferred. Verified 2026-08-25: 3,471,114/3,471,114 and 1,137,938/1,137,938 rows stamped, across 2 companies. (`inventory_on_hand` is far smaller since 2026-09-08 — see below; the backfill claim still holds, the row count does not.)

**Baseballism entity id:** `3bd934c9-4cdd-429b-9076-f8f6b45d4eb7`

**Onboarding flow (two paths):**
- **Founding a NEW organization is invite-gated** (changed 2026-09-18, `20260918120000`). It used to be open self-signup — `handle_new_user` read `org_name` from the auth metadata and provisioned the whole tenant — but `signUp` is a public endpoint and the anon key is published by design, so that key was caller-controlled input and anyone could found a tenant. That branch is gone; a signup with no invite now yields a bare profile with no company. Blake mints a link with `create_platform_invite` (gated by `is_platform_admin()`, a `platform_admins` table seeded with him alone — deliberately not "any owner_admin", since founding spends this project's quota), the prospect completes `/v2/company-onboarding.html?invite=TOKEN`, and `redeem_platform_invite` creates entity + `owner_admin` membership + `company_settings` in one transaction. **It writes the global `profiles.role`/`department`/`is_active` ONLY when the founder belongs to no other org, and REFUSES outright when the account is disabled** — the same rule `accept_org_invite` already follows, and for a sharper reason here: `can_manage_journal_entries()` admits `p.department in ('finance','exec')` on its own, independent of membership, so writing `department = 'exec'` for an existing member of another company would hand them journal-entry authority *there*, granted by founding *here*. Authority over the new company comes from the membership, which is per-company. `is_active` is the same kind of global flag and was the sharper case: deactivation does not remove memberships, so an account disabled by company A could have founded B and had A's deactivation silently undone — every authorization helper gates on that one column. A disabled account now cannot found a company at all. **The redeem is idempotent, not merely atomic**: the invite stores `created_company_id`, so a lost response and a second click return the SAME company (`repeated = true`) rather than founding a second one — the token is the idempotency key. Landing page is `/v2/setup-checklist.html`
- **Joining an existing org** is invitation-only: an admin creates an invite in `/v2/backend.html` (`create_org_invite` RPC → link `/pages/login.html?invite=TOKEN`, emailed via the `org-invite-send` edge function with manual-copy fallback); a brand-new invitee gets a "set password & join" screen (`org-invite-redeem` edge function creates the confirmed account and applies the invite — no confirmation email); an invitee with an existing account signs in and the login page redeems via `accept_org_invite`. Both paths activate the profile, apply role/department, and create the `entity_memberships` row. Tokens are sha256-hashed in `org_invites` (RLS deny-all, RPC-only), expire in 14 days, and are email-bound. Access-request approval and backend role grants also create the membership. Backend admin RPCs are scoped to the caller's active company plus unclaimed profiles (no membership anywhere)

**Active-company flow:**
1. Login calls `resolveCompany()` → reads `entity_memberships`
2. Single company → `set_active_company(entity_id)` RPC called automatically
3. Multiple companies → user routed to `/v2/company-picker.html` to pick, then RPC called
4. RPC writes `profiles.active_company_id` for the session
5. All RLS policies use `company_entity_id = active_company_id()` — only active company data visible

**RLS helper functions:**
```sql
active_company_id()                    -- reads profiles.active_company_id for auth.uid()
set_active_company(p_entity_id uuid)   -- validates membership then writes active_company_id
```

**Views:** All 30+ views in the public schema have `security_invoker = true` so RLS propagates through views, not just on base tables.

**JS pattern on every page:**
```js
const _co = await window.__SILO_CONFIG__?.ensureActiveCompany?.(db) || null;
// then on every SELECT of a company-scoped table:
if (_co?.id) query = query.eq('company_entity_id', _co.id);
```
Older pages still call the sync `getActiveCompany()`; prefer `ensureActiveCompany(db)` in new code
(see "Config and auth" for why). On inserts, wrap the payload in `withCompany()` / `withCompanyRows()`.

**Isolation status:** every operational table is isolated, `inventory_on_hand` and `sales_by_day` included. Both have RLS enabled with `select` and write policies scoped to `company_entity_id = active_company_id()` (verified 2026-08-25 against `pg_policies`). The backfill that older notes call deferred was completed — see `.github/workflows/backfill-company-entity-large-tables.yml`. A new company still needs its own sync pipeline to POPULATE these tables, but that is a data-availability question, not an isolation gap.

### Role system
Roles are **per-company**: permission gates judge by `entity_memberships.role` (`owner_admin` | `admin` | `member` | `viewer`) for the caller's ACTIVE company. `profiles.role` (enum `app_role`: `owner`, `admin`, `executive`, `user`) is the legacy global role — gates fall back to it only when the user has no membership row, and the profile-level `executive` still passes exec gates everywhere.
- membership `owner_admin`/`admin` (or profile fallback `owner`/`admin`) get write access to PO tables
- `executive` (profile-level) outranks `admin`: it passes `is_admin()` and additionally gates review-template building; `owner_admin` also passes `is_exec_or_owner()`
- `member`/`viewer` (or profile `user`) are read-only on PO tables
- Performance Reviews is the one module that ignores this hierarchy on purpose: rostering and running reviews needs no admin/exec role at all — any active user can manage the reports linked to them in `employee_managers` (via `is_employee_manager()`; `employees.manager_user_id` is informational-only and is NOT the authorization source); only `is_exec_or_owner()` (Blake) sees/manages the whole company roster, and only `is_exec_or_owner()` can build templates
- Invites and backend role grants set the membership role for that org; they only touch the global profile role/department when the user belongs to no other org
- blake@baseballism.com is `owner` (membership `owner_admin`); the other 6 users are `admin`

**Important:** `profiles.role` is an ENUM, not TEXT. Always cast with `role::text` when comparing in SQL.

### Write-access functions
```sql
is_admin_user()          -- SECURITY DEFINER since 2026-09-04, for COST not reach. Reads only the CALLER'S OWN rows in `profiles` and `entity_memberships`, both of which carry permissive own-row select policies, so the answer is identical either way -- but as INVOKER every call re-evaluated profiles' three RLS policies (two of which call functions that query profiles again): measured 755ms per 176 calls against 15ms for the DEFINER equivalent. It sits in 47 policies across 31 tables, so that cost landed on every PO, mailroom, payment-request, products and inventory page, and it is what made seven dashboard tiles reading po_headers hit the 30s statement timeout. Verified unchanged across all 34 real users before/after (32 admins, 2 non-admins, zero differences)
po_builder_can_write()   -- gates write on factories, po_headers, po_lines
po_costing_can_write()   -- gates write on po_costing, po_costing_lines
is_exec_or_owner()       -- gates review-template writes (owner, executive) and whole-company roster visibility
reviews_can_manage()     -- true for any active SILO user; per-row scoping (own reports vs. sees-everyone) lives in each policy's manager_user_id/is_exec_or_owner clause, not here
is_employee_manager(p_employee_id)  -- SECURITY DEFINER (bypasses RLS internally, like active_company_id()) so employees/employee_goals/reviews/employee_managers policies can check "is auth.uid() one of this employee's managers" without a raw EXISTS against employee_managers, which recurses into that table's own RLS
employee_has_open_comp_request(p_employee_id)  -- SECURITY DEFINER, same bypass pattern: "does this employee have a comp request that has actually been submitted (status <> 'draft')". Exists so employees_active_select can let a FINANCE reviewer read the one employee a queued request is about, without a raw EXISTS against comp_adjustment_requests (which would recurse into that table's RLS, which itself calls is_employee_manager back into employees). Added 2026-08-25 after impersonation testing showed finance passing the comp gate but seeing an EMPTY Finance Queue: the page renders comp_adjustment_requests_v, which INNER JOINs employees, and the view is security_invoker -- so employees' RLS ran inside it and dropped every row for a reviewer who manages nobody. It does NOT widen the review roster: an employee with no submitted comp request stays invisible to finance
is_employee_creator(p_employee_id)  -- SECURITY DEFINER, same bypass pattern: "is auth.uid() the profiles.id recorded in employees.manager_user_id" without a raw EXISTS against employees, which employees_active_select would deny for a brand-new employee with no employee_managers link yet (self-service creation's bootstrap step)
can_manage_silo_notes()  -- is_exec_or_owner() OR a silo_chat_managers grant for the caller's active company; gates silo_chat_notes writes so Ask SILO access can be handed out without promoting someone to executive company-wide
can_manage_journal_entries()  -- gates every card-coding table and the QBO post. Same population as the comp gate (membership owner_admin, or profile owner, or department finance/exec) and deliberately NOT is_admin_user(), which passes for any membership 'admin' -- 28 of 29 Baseballism profiles are membership 'admin', so that gate would let nearly the whole company post journal entries to the general ledger
can_manage_client_invoices()  -- may the caller bill their active company's customers through Stripe Connect, and read what is owed. Same population as can_manage_journal_entries() (membership owner_admin, profile owner, or department finance/exec) and deliberately NOT is_admin_user(), which passes for any membership 'admin' -- 28 of 29 Baseballism profiles are membership 'admin', so that gate would let nearly the whole company issue invoices to real customers in the company's name. A SEPARATE function rather than a reuse of the journal gate, because "may post to the ledger" and "may bill a customer" are different authorities that will diverge -- exactly as current_user_can_manage_comp_requests() diverged from the AP gate it was copied from
stripe_resolve_event_company(endpoint, account, customer)  -- SECURITY DEFINER, service-role only. The ONE definition of which company a Stripe webhook belongs to: a connect event resolves by its account id, a platform event by its customer id, and a PLATFORM event carrying an account id RAISES rather than being attributed -- that is what crossed endpoint signing secrets look like, and attributing it would file a tenant's own sales as SILO subscription revenue. Deliberately not metadata-driven: an account id is issued by Stripe and recorded here, whereas metadata on a connected account is writable by the client who owns it. An unknown account returns NULL and the caller records `unresolved`, never a guess
stripe_sync_invoice / _invoice_customer / _connect_account / _subscription / _billing_invoice  -- SECURITY DEFINER, revoked from anon AND authenticated (Supabase's default privileges grant EXECUTE on new public functions to both, so the revoke is the boundary -- 20260904330000 is the precedent). The ONLY writers of the Stripe mirrors, shared by the edge functions and the webhook so there is one definition of what a mirrored row is. Each takes the time of the FETCH and returns early on anything older, which is what makes out-of-order webhook delivery harmless; `stripe_drop_stale_sync` (BEFORE UPDATE) repeats the test for any writer going round them, since the service role bypasses RLS and a policy could not be that backstop
normalize_merchant(text)  -- IMMUTABLE. Collapses a card descriptor to a stable merchant key: strips the processor prefix (SQ *, TST*), a '*'-introduced reference code, trailing store digits, and a trailing alphanumeric code. Stripping only trailing DIGITS is not enough and fails on the highest-volume vendor -- 'AMZN Mktp US*2A4XY9' keeps its order code, so every Amazon charge becomes its own merchant and no rule matches twice. `/v2/card-coding.html` MIRRORS this function in JS; changing one without the other silently stops rules matching, which is why verify_v2_schema.sql asserts three specific inputs rather than just the function's existence
silo_business_today() / silo_business_yesterday()  -- **Company-aware since 20260918120000**: both read `company_settings.business_timezone` via `silo_business_timezone()`, falling back to Pacific when there is no active company (every service-role sync). Signatures, return types and volatility are unchanged, so the 19 callers and every seeded report were untouched. The business runs on PACIFIC; `current_date` is UTC and is a day ahead from 17:00 Pacific onward. Any report anchoring a period on `current_date - 1` therefore headlines a PARTIAL day as "yesterday" for the last seven hours of every working day -- measured 2026-09-03 00:06 UTC: current_date-1 gave 2026-09-02 (still selling) where Pacific yesterday was 2026-09-01. It also opens a reconciliation gap, since the UTC window reaches into days the sales matview has not covered ($10,220 on YTD; zero once anchored correctly). Use these helpers, never `current_date`, for anything a person reads as a day. **The sweep is finished (`20260924130000`-`130400`)**: every day boundary in the database reads the company's own timezone through ONE helper, `silo_company_timezone(company)`, which is the only place the Pacific fallback is written -- `verify_v2_schema.sql` goes CRITICAL if `'America/Los_Angeles'` reappears in any other public function or view (same guard as the `'online'` literal). The forecast ledger and `seo_task_publications` store the timezone ON THE ROW (`business_timezone`, stamped by trigger, frozen): the ledger's CHECK and generated column cannot look anything up, and a recorded event must not have its business day reclassified when the company later edits its timezone. The five SCRIPT sites that still reason in Pacific (Shopify forced rebuild, ad-platform window, Search Console window -- Google's days ARE Pacific -- the freshness alarm, `v2/daily-trend-kpis.js`) do so deliberately as a BOUND: Pacific is the westernmost supported zone, so for any supported company they are conservative, never wrong, and `scripts/tests/business-timezone-westmost.test.mjs` fails if a zone west of Pacific is ever added. `supported_business_timezones` now holds the four US mainland zones plus Arizona; Alaska and Hawaii need a sync-schedule change first (08:30 UTC is still their previous evening)
saved_report_usage(p_report_id uuid)  -- SECURITY DEFINER. The blast radius of editing a saved report: widget/dashboard counts, the highest query_index any widget points at, the columns those widgets name, and the parameter keys their dashboards supply. DEFINER because `dashboard_widgets` RLS scopes reads to dashboards the CALLER can see, so counting from the browser misses widgets on a colleague's private board -- and an undercount in a safety warning reads as safety. The tenant check is written out by hand since RLS is bypassed, and a report the caller cannot see returns NO ROWS AT ALL rather than a zero row (zero would confirm the id is real). Returns counts and column names only, never dashboard or widget titles. `supplied_parameters` is RAW -- a board's filter_state also holds keys belonging to other reports on it, so the editor intersects
current_user_can_manage_comp_requests()  -- NARROWER than current_user_can_manage_payment_requests() since 2026-08-25: membership owner_admin (or profile owner), or profile department finance/exec. It began as a verbatim copy of the AP gate, which passes for ANY membership 'admin' -- and 28 of 29 Baseballism profiles are membership 'admin', so that copy let nearly the whole company read and decide every comp request (salary figures included). This is the divergence the original migration anticipated. Executives keep access regardless: every policy calling it also ORs in is_exec_or_owner(). Gates who can move a comp_adjustment_requests row past 'draft'
```

The PO functions check `profiles` for `auth.uid()` and role in (`owner`, `admin`).

**`chat_run_readonly_query(query text, p_offset integer default 0)` is the shared reporting engine, not an Ask SILO detail.** **It returns `json`, NOT `jsonb`, and that is load-bearing** (fixed 2026-09-04): jsonb stores object keys sorted by (length, then bytewise), so `jsonb_agg` silently reordered every result's COLUMNS -- a report selecting `product_title, product_type, units_sold, net_sales, days_with_sales` came back as `net_sales, units_sold, product_type, product_title, days_with_sales`, and every table tile in `/v3/` drew it that way from the day the runtime shipped. `json_agg` preserves the select list; jsonb cannot at any cost, because key order is not part of its data model. Do not "tidy" the return type back to jsonb.
Despite the name it is generic: SECURITY INVOKER (so every read is scoped by the caller's own RLS),
single `SELECT`/`WITH` only, 1000-row cap per page (raised from 500 in 20260904320000), 30s statement
timeout. `p_offset` pages through anything larger -- a call that omits it behaves exactly as it always
has, page 1 only. `/v3/` uses it for two paginated surfaces: the report builder's Preview ("Load next
1000 rows") and table-visual dashboard widgets ("Load more", tracked per-widget and appended rather than
re-rendered so a reader mid-scroll doesn't lose their place) -- see `v3/README.md`'s Pagination section.
Charts do not page: a bar/line/donut/KPI/matrix is a computed shape over whatever page it drew, and
reshaping it live under someone reading it would be worse than the existing cap-hit note. Ask SILO's tool
loop, Ask SILO's "Refresh data" button, and every `/v3/` dashboard widget all run through it. A future
analyst-defined or standard SILO report should too — put new authoring experiences in front of this
engine rather than building a second one.

### Storage buckets
**Access is scoped through the PARENT ROW, not the bucket (fixed 2026-09-04, `20260904120000`).** Until then all 27 policies on `storage.objects` gated on `bucket_id` alone -- `using (bucket_id = 'payment-request-files')` -- so any authenticated user of any company could read or delete all 375 payment-request attachments and 51 mailroom scans. Private buys nothing on its own: private means the CDN will not serve the file anonymously, RLS decides who may. Every private bucket writes its parent row's id as the FIRST path segment (`<payment_request_id>/<file>`), so the policy is a plain `EXISTS` against the parent table and the object inherits that table's RLS -- no SECURITY DEFINER, no second definition of who may see what. Keyed on the PARENT row, never the `*_files` metadata row, because the object is uploaded BEFORE its metadata row exists and keying on metadata would make a failed-insert upload permanently undeletable. A PUBLIC bucket keeps public reads on purpose (served at `/object/public/...` with no RLS evaluated at all, so a SELECT policy there cannot hide anything); only its writes are scoped. `docs/ops/storage-isolation.md` has the table and the impersonation test. **When adding a bucket, put the parent id first in the path and write the policy as an EXISTS -- do not copy an existing policy body**, which is how `schedule-item-files` shipped with three policies NAMED "by company" and no company clause in any of them.
- `payment-request-files` — private, payment request attachments
- `launch-images` — public, launch workbench image uploads
- `mail-item-files` — mailroom attachments (`mail_item_files`)
- `avatars` — profile avatars
- `sample-images` — product sample / tracker images
- `product-concept-images` — public, Ask SILO Product Concepts reference/inspiration image uploads (in testing)
- `customer-account-files` — private, wholesale customers' resale certificates. Its policies' `EXISTS` names `customer_account_tax_profiles`, **not** `customer_accounts`, so the object inherits the NARROW gate rather than the directory's. There is deliberately no anon policy: the applicant is unauthenticated and uploads through a service-role-minted signed URL, which bypasses RLS, so an anon policy would be a hole with nothing behind it
