stripe-webhook   -- PUBLIC (verify_jwt off): the single receiver for BOTH Stripe surfaces. **`checkout.session.completed` is now in BOTH routing tables and means two different things** -- on the platform a tenant subscribing to SILO, on connect a wholesale applicant saving a card against the TENANT's customer (`connect_setup`) -- which is exactly why the endpoint is decided by the signing secret before the table is consulted. The connect path re-fetches the session, IGNORES anything whose `mode` is not `setup`, and then **establishes that the session is SILO's BEFORE it changes anything at Stripe** (`customer_card_setup_session_owner`, read-only): a tenant owns their Connect account outright and can run a setup-mode Checkout from their own dashboard, and those events arrive on this same endpoint and resolve to the same company -- so "setup mode, company we know" is not evidence the session is ours, and acting on one would re-point the invoice default on a customer SILO was never asked about. Only then does it retrieve the SetupIntent, check its customer against the account's binding, record the card as NOT default, and **explicitly sets `customer.invoice_settings.default_payment_method`**: Checkout ATTACHES the method but does not make it the invoice default, and an invoice against a customer with no default sits open. The card is recorded BEFORE that call, so one attached at Stripe is never missing from SILO because a follow-up failed. A failure is then CLASSIFIED (`isTerminalStripeError`): a terminal 4xx is recorded and left, with `default_payment_method_set_at` null so "saved but not yet default" is a visible state rather than a silent half-configuration; a 5xx, a 429 or a dropped connection is RETHROWN so the webhook's retry ledger redelivers it -- swallowing those is how a card becomes permanently unusable by invoice automation, since the account reads `succeeded` and `start_card_setup` then answers `already_captured`, so nothing ever retries. `checkout.session.expired` releases the claim (`connect_setup_expired`). One function, not two, because the two endpoints deliver the same event TYPES and the whole risk is confusing them -- the decision lives in `routeEvent()` with one test file over it. The endpoint is decided by WHICH SIGNING SECRET VERIFIES the signature (platform secret tried, then connect), never by inspecting the payload. Every handler RE-FETCHES the object and syncs what came back, so a retry of a three-minute-old event cannot revert a paid invoice to open. Secrets: STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, STRIPE_CONNECT_WEBHOOK_SECRET

only via `pg_get_functiondef`, not by reading this repo. **Also found in the same pass:** the deployed function
list includes `bright-action`, `replace-product-tags`, and `oneoff-meta-sync` — none documented here, none with
an obvious source file in `supabase/functions/`. Do not assume `supabase/functions/` is the complete list of
deployed functions, and when working on any table that already has triggers, check `pg_trigger` /
`pg_get_functiondef` directly rather than grepping migrations — a grep-only search missed
`notify_slack_sample_created()` here and nearly caused sample-notify to double-post to Slack on every new sample.
Emails send via Resend (`RESEND_API_KEY` edge-function secret — separate key from the auth SMTP one). **The sender address is configuration, not a constant, since 2026-09-18**: ten functions read `SILO_MAIL_FROM` and fall back to `SILO <noreply@silo-baseballism.com>`, so nothing changes for Baseballism until that secret is set. It exists because a second tenant's invite, review or payment email arriving from a Baseballism address reads as a mistake, or as a leak of who else uses SILO. Setting it requires redeploying those ten functions — merging does not deploy, and `deployment-drift-check.yml` is red for them until it happens. Link base URL: `SILO_SITE_URL` env or hardcoded `https://silo-baseballism.com`. Without the key, sending still works — the manager gets the link to deliver manually. `payment-request-forward-melio` additionally requires `MELIO_FORWARD_EMAIL` (the company's Melio auto-scan forwarding address, e.g. `baseballism_NNN@invoicesmelio.com`) — set as an edge-function secret, never hardcoded or exposed client-side. `sample-notify` additionally reads `SLACK_SAMPLES_WEBHOOK_URL` (a Slack Incoming Webhook URL, for the shared #samples-channel post) and `SLACK_BOT_TOKEN` (a Slack bot token with `users:read.email` + `im:write` + `chat:write` scopes, for per-assignee DMs) — both optional and independent of each other; neither is configured as of this writing, so Slack delivery is currently a no-op until someone creates the webhook/app and sets the secrets. Email delivery does not depend on either.
